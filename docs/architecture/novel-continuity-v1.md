# 小说连续性系统 V1 实施决策

## 目标与边界

NovelStudio 的核心不是多 Agent 对话，而是可追溯、可验证、可回滚的故事权威状态（Canon）。LLM 负责候选正文与语义判断，程序负责版本、权限、确定性约束和原子提交。

V1 聚焦单部小说、单条主线和人工批准，先完成一章从章节契约到 Canon 提交的纵向闭环。电影解说、技术文档和复杂协作权限不作为连续性内核的验收前提。

## 领域模型

- Entity：人物、地点、组织、物品、能力等稳定对象。
- Fact：带来源、有效故事时间、认知范围和 Canon 分支的陈述。
- Event：故事时间中的事件，记录参与者、地点和来源章节版本。
- State Transition：事件引起的字段级状态变化，保存 before、after 和证据。
- Canon Commit：不可变变更集；正文版本、事实、事件和状态变化共同提交。

事实区分故事时间与系统记录时间，并保留 `known_by`、`revealed_to_reader_at`、`certainty` 和 `branch_id`。高频关系使用显式表和索引，JSON 只保存低频扩展信息。

## 提交不变量

1. 提交声明 `base_canon_version`；与当前版本不一致时冲突。
2. 事实、事件和状态变化必须引用章节版本及原文证据。
3. 状态变化的 `before` 必须等于基准 Canon 的当前值。
4. 事件引用的实体必须已存在或在同一变更集中创建。
5. 任一校验失败时，整个变更集不可见。
6. MySQL 是运行时权威源；Git、向量索引和摘要是可重建派生数据。
7. 派生数据通过 transactional outbox 更新，不冒充数据库事务的一部分。

## 上下文与审稿

每次模型调用保存不可变 Context Manifest：Canon 版本、章节起始状态、事实与证据版本、检索参数、排序和裁剪原因、Prompt/模型参数及 Token 用量。

连续性校验遵循“确定性规则优先，LLM 补充”：死亡、时间重叠、移动、物品数量、认知越界和过期依赖由程序判断；动机、OOC、铺垫和文风交给模型。

## V1 验收场景与顺序

修改早期章节的人物状态后，系统能找出依赖旧状态的后续章节，展示证据、标记 stale，并阻止未经批准的新 Canon 传播。

1. Canon 领域模型、原子变更集和内存实现。
2. MySQL 事务持久化与 outbox。
3. Canon/影响分析 API。
4. Context Manifest 接入生成流程。
5. 确定性规则、人工标注回归集和审批工作台。
